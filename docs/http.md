# Клиент HTTP

`tnt-http` — клиент HTTP для Tarantool поверх встроенного `http.client`,
то есть libcurl. Адрес с параметрами, тело в JSON и в форму, сроки,
переходы, повторы и поток собраны в одном месте, и решения в них приняты
за вызывающего.

```lua
local api = assert(require('tnt.http').new({ base_url = 'https://api.example.org/v1', timeout = 3 }))
local answer, err = api:get('/customers', { query = { page = 2, tag = { 'новый', 'важный' } } })
local customers = answer and answer:raise():json()   -- nil, err — ответа нет; 404 и 500 — ответы
```

Зависит от [`tnt-retry`](https://github.com/tnt-skein/tnt-retry) (паузы
повторов и судья отказов), [`tnt-context`](https://github.com/tnt-skein/tnt-context)
(опознаватель запроса и заголовки трассы из контекста файбера),
[`tnt-validate`](https://github.com/tnt-skein/tnt-validate) (проверка
настроек), [`tnt-log`](https://github.com/tnt-skein/tnt-log) (журнал),
[`tnt-must`](https://github.com/tnt-skein/tnt-must) (проверки аргументов)
и [`tnt-external`](https://github.com/tnt-skein/tnt-external) (подмена
libcurl в проверках).

## Зачем пакет

Ходить в чужие службы приходится постоянно: хранилище конфигурации,
объектное хранилище, поисковая система, чужое API. Встроенный
`http.client` это умеет, но всё, на чём спотыкаются, оставляет
вызывающему: собрать адрес с параметрами, закодировать тело, разобрать
ответ, решить, что делать с 503, не повторить платёж дважды и не отдать
пароль чужому узлу на переходе. Каждый клиент чужой службы пишет этот
обвес заново, и каждый чуть иначе. Пакет держит его в одном месте:

- **Адрес и тело.** Базовый адрес — приставка пути, параметры кодируются
  по RFC 3986 и идут в постоянном порядке, список уходит повторённым
  именем; `json` и `form` ставят свой `content-type` сами.
- **Отказ отдельно от ответа.** Нет ответа — `nil, err`, где `err` —
  таблица с родом и приговором; ответ 404 или 500 — это ответ.
- **Переходы и повторы по правилам HTTP.** Переходы клиент проходит сам:
  считает их, снимает заголовок входа при уходе на чужой узел и ходит
  только по `http` и `https`. Повторяет только идемпотентные методы
  и только отказы, которые лечит время, с уважением к `Retry-After`.
- **Пределы по умолчанию.** Срок, число переходов и размер ответа
  включены сразу: чужой сервер не обязан быть дружелюбным.
- **Поток.** Тело, которое не кончается или не помещается, читается
  кусками, с пределом на сумму и на кусок.
- **Опознаватель запроса и трасса** уезжают в каждую попытку сами —
  из контекста файбера, без единой строки в прикладном коде.
- **Незнакомая настройка — отказ**, а не молчаливое «не действует»:
  `timout = 1` не оставляет срок в десять секунд.

## Как пользоваться

| Вызов | Что делает |
|---|---|
| `http.new(opts)` | заводит клиент со своими настройками и своим кэшем соединений; отказ — `nil, err` |
| `client:request(opts)` | выполняет запрос; ответ с любым кодом либо `nil, err` |
| `client:get(url, opts)`, `:post`, `:put`, `:patch`, `:delete`, `:head` | то же с методом и адресом |
| `client:stream(opts)` | открывает поток: тело читается кусками |
| `client:status()` | что настроено — без секретов |
| `http.configure(opts)` | настраивает общий клиент процесса; отказ — `false, err` |
| `http.default()` | общий клиент; заводится при первом обращении |
| `http.request`, `http.get`… `http.stream`, `http.status` | те же вызовы общим клиентом |
| `http.hook(name, hook)`, `http.hooks()` | крюки вокруг каждой попытки и открытия потока |

### Запрос и ответ

```lua
local http = require('tnt.http')

local answer, err = http.get('https://api.example.org/customers', {
    query = { page = 2, tag = { 'новый', 'важный' } },
    headers = { Authorization = 'Bearer …' },
})

if answer == nil then
    return nil, err                    -- ответа нет; err.kind скажет почему
end

if answer.status == 404 then
    return nil, 'клиента нет'          -- 404 — это ответ, а не отказ
end

local page = answer:raise():json()     -- бросает на коде вне 2xx
```

Адрес уходит таким:
`https://api.example.org/customers?page=2&tag=%D0%BD%D0%BE%D0%B2%D1%8B%D0%B9&tag=%D0%B2%D0%B0%D0%B6%D0%BD%D1%8B%D0%B9`.

Ответ — таблица с методами:

| Поле | Что значит |
|---|---|
| `status` | код ответа |
| `reason` | слово `http.client` о коде; пустая строка, если слова нет |
| `headers` | заголовки; имена в нижнем регистре |
| `body` | тело; у HEAD и 204 — пустая строка |
| `url` | адрес, с которого ответ получен, — после переходов |
| `method` | метод, которым ответ получен |
| `answer:ok()` | код из 2xx |
| `answer:json()` | разбор тела как JSON; отказ — `nil, err` с началом ответа |
| `answer:raise()` | бросает на коде вне 2xx, иначе возвращает сам ответ |

Имена заголовков ответа приведены к нижнему регистру: в HTTP регистр
имени не значит ничего, а код, читающий `Content-Type` по точному имени,
работает ровно до смены сервера. Заголовки запроса приводятся так же —
`Content-Type` клиента и `content-type` запроса не уедут на сервер
вдвоём.

`raise()` бросает строку с методом, адресом, кодом и началом тела —
без файла и строки пакета: падение случилось у чужого сервера.
Пригождается там, где чужой отказ и есть конец работы: обход, разовая
задача, миграция. В обработчике запроса вернее `ok()`.

`json()` на пустом теле и на странице ошибки прокси отказывает парой,
а не бросает, и называет начало того, что пришло, — первые 200 знаков:

```lua
answer:json()   --> nil, 'ответ не разобран как JSON: …; начало ответа: <html>…'
```

### Свой клиент и общий

Свой клиент — базовый адрес, общие заголовки, сроки и пределы на все
запросы, свой кэш соединений libcurl:

```lua
local api = assert(http.new({
    base_url = 'https://api.example.org/v1',
    headers = { authorization = 'Bearer …' },
    timeout = 3,
    max_redirects = 3,
    max_body = 1024 * 1024,
}))

api:post('/customers', { json = { name = 'Иванов' } })   -- POST https://api.example.org/v1/customers
```

Путь базового адреса — приставка, а не корень: у `https://s/v1`
и запроса `/users` получается `https://s/v1/users`, хотя разрешение
ссылки по RFC 3986 потеряло бы `v1`. Базовый адрес задают как раз затем,
чтобы не повторять `v1` в каждом вызове. Косые черты на стыке сводятся
к одной: `https://s/v1/` и `users`, `https://s/v1` и `/users` дают один
и тот же адрес. Адрес со схемой в запросе базовый адрес не трогает,
а относительный адрес без базового — отказ `invalid`: «адрес «/customers»
неполон: задайте клиенту base_url или пришлите адрес со схемой».

Настройки запроса ложатся поверх настроек клиента на один вызов:
`api:get('/report', { timeout = 60 })`. Сама таблица настроек запроса
не меняется — её можно держать у себя и слать по ней несколько запросов.

Общий клиент один на процесс. `http.configure(opts)` проверяет настройки
сразу и забывает собранный клиент: следующее обращение соберёт новый,
иначе прежний кэш соединений жил бы с новыми настройками. До первого
обращения обработчик libcurl не заводится вовсе.

```lua
assert(http.configure({ timeout = 5, headers = { ['x-service'] = 'billing' } }))

http.get('https://api.example.org/health')   -- общим клиентом с этими настройками
http.configure({ timout = 5 })               --> false, 'неизвестная настройка timout'
```

### Настройки

| Настройка | Умолчание | Что значит |
|---|---|---|
| `base_url` | нет | начало адреса, к которому дописываются пути; только клиенту |
| `headers` | нет | заголовки; значения приводятся к строке |
| `timeout` | `10` | срок ответа, секунды, не меньше 0,001 |
| `connect_timeout` | `3` | срок соединения; складывается со сроком ответа (см. «Сроки») |
| `max_redirects` | `5` | предел переходов по `Location`; `0` — не переходить; потоку не задаётся |
| `max_body` | `8388608` | предел размера ответа в байтах (8 МБ); `0` — без предела |
| `max_connections` | `8` | размер кэша соединений libcurl; только клиенту |
| `verify` | `true` | проверять сертификат сервера и имя в нём |
| `ca_file`, `ca_path` | нет | файл и каталог доверенных корней |
| `ssl_cert`, `ssl_key` | нет | файлы клиентского сертификата и его ключа |
| `unix_socket` | нет | сокет, через который идти |
| `accept_encoding` | `'gzip, deflate'` | какое сжатие просить; разжимает libcurl сам |
| `user_agent` | `'tnt-http'` | чем представляться серверу |
| `retry` | как у `tnt-retry` | настройки повторов клиенту и отдельному запросу; потоку не задаются |
| `layers` | `{}` | слои запроса; только клиенту |
| `propagate` | `true` | класть ли заголовки контекста и звать ли крюки; только клиенту |

Запрос принимает сверх того `method` (по умолчанию `GET`), `url`
или `path` — одно и то же, `query`, `json`, `form` и `body`. Поток —
те же поля, кроме `max_redirects` и `retry`, и ещё `duplex` и `max_piece`
(см. «Поток»).

Проверяется всё и сразу — при сборке клиента и перед каждым запросом,
до первого байта. Настройка клиента задаётся однажды и живёт годами,
а её ошибка проявляется, когда чужая служба и так лежит:

```lua
http.new({ timout = 1 })        --> nil, 'неизвестная настройка timout'
http.new({ verify = 'false' })  --> nil, "проверка сертификата должна быть логическим значением, а не 'false'"
http.new({ timeout = 0 })       --> nil, 'срок ответа должен быть числом не меньше 0.001, а не 0'
```

`timout = 1` иначе оставил бы срок в десять секунд, и не сказал бы
об этом никто. `verify = 'false'` строкой выключил бы проверку
сертификата ровно в том смысле, в каком строка `'false'` истинна, —
то есть никогда. Срок, равный нулю, у libcurl значит «без срока» — ровно
обратное тому, что имел в виду написавший `timeout = 0`. Отказ в запросе —
та же беда, но таблицей рода `invalid`:
`api:get('/x', { max_redirect = 1 })` → `nil, err`, `err.kind == 'invalid'`.

### Параметры запроса: `query`

| Значение | Что уходит |
|---|---|
| строка, число | `name=значение`, всё вне `A–Z a–z 0–9 - . _ ~` — байтами `%XX` |
| `true`, `false` | `name=true`, `name=false` — словом, а не `1` и `0` |
| список `{ 'a', 'b' }` | `name=a&name=b` |
| `box.NULL` | ничего: значения нет |

Параметры идут по имени в алфавитном порядке, а не как придёт
из `pairs`: иначе один и тот же запрос собирался бы каждый раз по-новому,
подпись запроса перестала бы сходиться, а проверка ловила бы ошибку через
раз. Пробел кодируется как `%20`, а не `+`: `%20` понимают и путь,
и параметр, и форма. Параметры, уже стоящие в адресе, остаются:
базовый адрес службы иногда несёт свой ключ.

```lua
http.url.with_query('https://api.example.org/customers', {
    page = 2, draft = false, gone = box.NULL, tag = { 'новый', 'важный' },
})
--> 'https://api.example.org/customers?draft=false&page=2&tag=%D0%BD…&tag=%D0%B2…'
```

Имя параметра — строка: `query = { 'a', 'b' }` — это не набор
параметров, и отправить его как `1=a&2=b` значило бы искать бессмыслицу
в чужом журнале. Отказ `invalid` — «имя параметра запроса должно быть
строкой, а не number»; функция в значении — «параметр a: значение
function нельзя записать в параметр запроса».

### Тело: `json`, `form`, `body`

```lua
api:post('/customers', { json = { name = 'Иванов' } })           -- application/json
api:post('/login', { form = { user = 'ivanov', remember = true } }) -- application/x-www-form-urlencoded
api:put('/avatar', { body = png, headers = { ['content-type'] = 'image/png' } })
```

`json` и `form` ставят `content-type` сами — забытый заголовок
содержимого самая частая причина ответа 415, — но только там, где его
не задали руками: написавший `application/vnd.api+json` имел это
в виду. Форма кодируется тем же кодировщиком, что и параметры адреса:
`application/x-www-form-urlencoded` — это и есть строка запроса в теле.

Способ задать тело ровно один: `json` вместе с `body` — два разных
намерения, и угадывать главное значило бы однажды угадать не так.
Отказы `invalid`: «тело задано дважды: json и body — оставьте что-то
одно», «body — это готовая строка, а пришло table: таблицу задают через
json или form». Таблица, которую `json.encode` не кодирует (ссылка
на себя, незнакомая cdata), — отказ «тело не собралось в JSON: …»,
а не брошенное исключение.

### Отказ, ответ и исключение — три разные вещи

Это главное соглашение пакета:

| Что случилось | Что вернётся |
|---|---|
| сеть недоступна, сервер молчит, срок вышел | `nil, err` |
| сервер ответил 404, 429, 500 | ответ со `status`, это не отказ |
| `answer:raise()` на ответе вне 2xx | исключение |

«Сервер сказал нет» и «сервер не сказал ничего» — разные события:
первое разбирает прикладной код — отдать своему клиенту 502, взять
значение из кэша, промолчать, — второе значит, что разбирать нечего.

`err` — таблица `TntHttpFailure`, а не строка: тот, кто ведёт свои
повторы, судит по роду, а не по словам.

| Поле | Что значит |
|---|---|
| `kind` | род отказа, см. ниже |
| `message` | причина с методом и адресом — для человека |
| `reason` | причина без адреса — для журнала: в параметрах ездят ключи |
| `retriable` | стал бы повторять сам клиент (только идемпотентные методы) |
| `status`, `retry_after` | код и `Retry-After`, если ответ был |

| `kind` | Когда | Лечит ли другой узел или время |
|---|---|---|
| `invalid` | запрос не собран: негодная настройка, адрес, тело, вызов потока не по правилам | нет — ошибка вызывающего |
| `unreachable` | ответа нет: сеть, срок, обрыв посреди тела | да |
| `refused` | клиент не отдал ответ сам: больше предела, переходов больше предела, переход не на `http(s)`, отказ слоя или крюка | нет |
| `status` | у потока: сервер ответил кодом не из 2xx (код приходит в конце) | по коду |
| `idle` | у потока: за срок чтения куска не набралось; поток открыт | — |

```lua
local answer, err = http.get('http://no-such-host.invalid/')

err.kind        --> 'unreachable'
err.retriable   --> true: GET клиент повторил бы сам
tostring(err)   --> "GET http://no-such-host.invalid/: сервер не ответил: Could not resolve hostname (код 595)"
```

Слова после «сервер не ответил» — libcurl, и зависят от его выпуска:
вывод выше снят на статической сборке Tarantool 3.8 для Linux
(libcurl 8.11), а libcurl старше 8.9 пишет «Couldn't resolve host
name». Кто судит по словам, сверяет их частью, общей для обоих
написаний, — `resolve host`, `connect to server`.

`unreachable` бывает и до отправки, и после. Отказ имени и соединения
`http.client` отдаёт придуманным кодом 595, а сброс соединения,
оборванное тело и мусор вместо ответа — исключением, когда сервер
запрос уже прочитал. Исключение клиент не роняет, а отдаёт тем же родом
с меткой «libcurl отказал»: `PUT http://h/x: libcurl отказал: curl:
Failure when receiving data from the peer: Connection reset by peer`.
Поэтому сам клиент повторяет `unreachable` только у идемпотентных
методов.

Строкой отказ читается текстом `message`: `tostring(err)`,
`('%s'):format(err)`, `'причина: ' .. err` и `json.encode({ err = err })`
дают этот текст. Строковых методов у таблицы нет: `err:find(...)`
падает — текст читают через `tostring(err)` или `err.message`.
`http.failure.is(err)` отличает отказ клиента от чужой таблицы.

Кто судит сам, судит по роду, а не по `retriable`: у кого свои правила —
etcd, например, ходит POST даже за чтением, — тому приговор клиента
не указ, а род отказа скажет, лечит ли его другой узел.

### Повторы

Повторяются только безопасные методы и только отказы, которые лечит
время, — через `tnt-retry`, со всем, что там есть: разброс пауз, общий
срок, бюджет, размыкатель. Настройки повторов задаются клиенту
и отдельному запросу полем `retry`:

```lua
local api = assert(http.new({
    base_url = 'https://api.example.org/v1',
    retry = { attempts = 4, base = 0.2, deadline = 10 },
}))

api:get('/customers/7', { retry = { attempts = 1 } })   -- этот запрос — без повторов
```

Повтор решается двумя вопросами подряд. Первый — можно ли повторять
действие: RFC 9110 (§9.2.2) называет идемпотентными GET, HEAD, OPTIONS,
TRACE, PUT и DELETE. **POST и PATCH не повторяются никогда**, даже когда
соединение оборвалось до ответа: клиент не знает, дошёл ли запрос,
и оборвавшийся после приёма платёж при повторе станет вторым платежом.
Нужен повтор записи — нужен ключ идемпотентности, то есть
[`tnt-once`](https://github.com/tnt-skein/tnt-once), а не клиент HTTP.

Второй — стоит ли повторять этот отказ. Отвечает судья `tnt-retry`:
408, 425 и 429 повторяются, 5xx повторяются, кроме 501 и 505 — «не умею»
и «не понимаю версию» чинит не время. Отказ сети у идемпотентного
метода повторяется: дошёл ли запрос, узнать неоткуда, а повторить его
безопасно.

Ответ, который стоит повторить, — 503 на GET — возвращается вызывающему
ответом, если попытки кончились: нужен он, а не рассказ о нём.
Заголовок `Retry-After` соблюдается, если сервер назвал число секунд:
пауза удлиняется до названной, а просьба дольше потолка паузы `max`
отменяет повтор совсем. Дата в `Retry-After` не разбирается: она
меряется часами сервера, а они расходятся с нашими.

Срок попытки режет остаток общего срока `deadline`: незачем начинать
попытку длиннее, чем вызывающий согласен ждать целиком. Остаток
спрашивается перед каждым обращением, и у переходов тоже: попытка
с тремя переходами иначе длилась бы втрое дольше.

**Повтор идёт к тому же адресу.** О равноправных узлах клиент не знает,
и настройки «куда идти на следующей попытке» у него нет нарочно:
соседнему узлу бывает нужен свой вход, свой токен и свой курсор. Кто
обходит несколько узлов сам, выключает повторы клиента —
`retry = { attempts = 1 }` — и ведёт свои по роду отказа. Иначе два
вложенных цикла перемножают обращения: лежащий узел получает девять
запросов вместо трёх.

Негодные настройки повторов — отказ при сборке клиента и отказ `invalid`
у запроса, до отправки: узнать о них надо до первого байта, а не отказом,
неотличимым от отказа сервера.

### Пределы

Оба включены по умолчанию, потому что чужой сервер не обязан быть
дружелюбным:

- **число переходов по `Location`** (`max_redirects`, 5) — иначе два
  сервера, ссылающиеся друг на друга, заняли бы файбер навсегда;
- **размер ответа** (`max_body`, 8 МБ) — иначе ответ на гигабайт съест
  память узла.

Ответ больше предела — отказ `refused` «ответ в N байт больше предела
в M», переходов больше предела — «переходов больше N, дальше не идём».
Предел переходов в ноль значит «не переходить вовсе»: ответ 3xx тогда
отдаётся вызывающему как есть.

Оговорка про размер важная: **предел — счёт отданного, а не память.**
libcurl отдаёт тело целиком и только целиком, и остановить чужой гигабайт
на середине из Lua нечем. Предел значит «столько клиент отдаст наверх»:
ответ больше предела превращается в отказ, и ссылки на него не остаётся
ни у кого, — но пик памяти на приёме уже случился.

Поток (`client:stream`) от пика памяти не лечит, хотя тело там читается
кусками. `http.client` принимает тело с той скоростью, с какой его шлёт
сервер, и копит у себя, пока поток открыт, — читают его или нет:
обратного давления у него нет. На опыте поток с `max_body` в мегабайт
за две секунды без чтения принял все 300 МБ, что прислал сервер: память
узла выросла с 33 до 632 МБ. Сжатое тело набивает её во столько раз
быстрее, во сколько сжато. Память потока ограничена только тем, как
быстро его читают, и **от враждебного или сжатого тела не защищают
ни запрос, ни поток.** Чужому серверу, которому нельзя доверять объём,
это надо закрывать не клиентом.

### Сроки: складываются

`connect_timeout` и `timeout` — не два отдельных срока, а слагаемые
одного. `http.client` 3.8 знает один срок на всё обращение — отдельного
срока соединения среди его опций нет, — и соединение идёт в его счёт.
Проверено запуском:

| Что | Срок | Сколько длилось |
|---|---|---|
| недоступный адрес `10.255.255.1` | `timeout = 1.5` | 1,500 с — весь срок, а не доля соединения |
| сервер принял соединение и молчит | `timeout = 1` | 1,001 с |
| тело течёт по байту 4 с | `timeout = 1` | 1,003 с — срок общий, а не срок тишины |
| живая проверка против httpbin | `connect_timeout = 0.4`, `timeout = 0.4` | 0,8 с |

Поэтому клиент ставит libcurl их сумму: при 2 и 5 секундах и недоступный
узел, и молчащий сервер держат попытку семь секунд. Раздельных сроков
этот клиент не обещает. Общий срок повторов (`retry.deadline`) режет
попытку дополнительно.

Срок, вышедший посреди тела, приходит от `http.client` с заголовками
и кодом 408 — `{status = 408, reason = 'Timeout was reached', headers = …,
body = 'xxx'}`. Клиент отличает его от ответа сервера по слову libcurl
и отдаёт отказом `unreachable`, а не обрезанным телом. Так же
не считаются ответом прочие коды, которые `http.client` придумывает сам,
когда ответа не было: 595 «не разрешилось имя» или «не соединилось»,
444 «ничего не пришло», 495 «сертификат не прошёл», и код 0 при любом
слове.

### Переходы: только веб

Переходы по `Location` клиент проходит сам, а не отдаёт libcurl: иначе
их не сосчитать — числа переходов `http.client` не принимает — и не снять
заголовок входа с чужого узла.

```lua
local answer = api:get('/old')   -- 301 Location: /v1/new
answer.url                       --> 'https://api.example.org/v1/new'
```

Метод меняется по RFC 9110 (§15.4): 303 велит забрать ответ методом
GET, 301 и 302 делают то же с POST — сервер, отвечающий 302 на отправку
формы, рассчитывает именно на это, — а 307 и 308 сохраняют и метод,
и тело. HEAD остаётся HEAD. Сменив метод на GET, клиент снимает тело
и его `content-type`. `Location` в ответе, код которого не переход
(201 указывает на созданный ресурс), клиент не проходит. Относительная
ссылка разрешается по RFC 3986 полностью: `Location` пишет сервер,
и вольничать с чужой ссылкой нельзя.

**Заголовок входа на чужой узел не едет.** `authorization`, `cookie`
и `proxy-authorization` снимаются, если узел — схема, имя и порт — после
перехода другой: сервер, ответивший `Location: http://evil/`, получил бы
токен доступа к соседней службе. `https://Example.org` и
`https://example.org:443` — один и тот же узел.

Цена ручного обхода — запрет, который libcurl держит на своих переходах
(`Unsupported protocol` на `file://` и `gopher://`), приходится держать
самим. Без него (проверено запуском):

- сервер, ответивший `302 Location: file:///etc/hosts`, получал бы файл
  узла телом ответа — и через TCP, и через сокет;
- переход на `gopher://127.0.0.1:<порт>/_…` отправлял бы произвольные
  байты на внутренний порт, а его ответ возвращался бы телом.

Поэтому клиент ходит **только по `http` и `https`** (схема в любом
регистре): адрес запроса или потока с другой схемой — отказ `invalid`
«схема «file» не годится: клиент ходит только по http и https»,
переход на другую схему — отказ `refused` «переход на схему «file»
не разрешён». Сверх того транспорт не считает ответом код 0: так
`http.client` отдаёт итог не-HTTP обращения — `file://` приходит с кодом 0
и словом «Unknown», тем же, что у настоящего ответа.

Так ведёт себя libcurl сборки Tarantool для macOS. Статическая сборка для
Linux приносит libcurl без схем `file://` и `gopher://`: там обращение
по ним отказывает ещё до отправки («libcurl отказал: curl: Unsupported
protocol»). Отказом клиента оба пути кончаются одинаково, а запрет схем
и сверка кода 0 держатся на случай сборки, которая эти схемы знает.

### Клиентский сертификат и сокет

```lua
local etcd = assert(http.new({
    base_url = 'https://etcd-1:2379',
    ca_file = '/etc/app/ca.pem',
    ssl_cert = '/etc/app/client.pem',
    ssl_key = '/etc/app/client.key',
}))

local docker = assert(http.new({ unix_socket = '/var/run/docker.sock' }))
docker:get('http://localhost/containers/json')
```

`ssl_cert` и `ssl_key` — пути, как их принимает libcurl. Есть ли файл,
при сборке клиента не проверяется: сертификаты подменяют на месте при
перевыпуске, и отказ на пути, которого сегодня нет, ронял бы сборку
из-за того, что появится завтра. Не нашедшийся файл называет libcurl,
и отказ доходит словами «Problem with the local SSL certificate».
В `status()` виден путь сертификата, а ключ — только признаком
`ssl_key = true`.

**Ключ без сертификата — отказ**: у клиента при сборке и у запроса после
слияния с настройками клиента — «ключ клиентского сертификата без
сертификата не действует: задайте ssl_cert». libcurl один ключ молча
пропускает и идёт без клиентского сертификата вовсе: сервер, который
сертификата не требует, обслужил бы запрос как безымянный, а требующий
оборвал бы рукопожатие отказом, неотличимым от сетевого (проверено).
Сертификат без ключа законен: ключ бывает в том же файле. Против etcd
с `--client-cert-auth` проверено: без сертификата разговора нет, с ним
проходят и запрос, и поток.

**Сокет — это дорога до узла, а не узел.** Адрес в URL остаётся
логическим: по нему ставится `Host`, по нему сличаются узлы на переходе
и снимается `Authorization`. Дорога одна на весь запрос, и все
переходы — на свой узел и на чужой — идут в тот же сокет; так её держит
и libcurl. С сокета клиент в сеть не выходит, из сети в сокет не попадает:
переход меняет адрес, но не дорогу и не протокол. Держится последнее
на запрете схем: без него переход на `file://` ушёл бы с сокета на диск
узла. Имя узла в URL при этом не разрешается вовсе:
`http://sidecar.invalid/` через сокет работает. У `https://` через сокет
сертификат проверяется по имени из URL.

### Поток

```lua
local stream, err = api:stream({ url = '/events', max_body = 0, max_piece = 64 * 1024 })

if stream == nil then
    return nil, err
end

while true do
    local line, failure = stream:read('\n', 30)

    if line ~= nil then
        handle(line)
    elseif failure == nil then
        break                         -- кончился удачно, stream.status известен
    elseif failure.kind ~= 'idle' then
        break                         -- обрыв, предел, код не из 2xx
    end
end

stream:close()
```

Нужен там, где ответ не кончается или не помещается: наблюдение
за ключами etcd (`/v3/watch`), выгрузка построчно, события сервера.
Обычный запрос для этого не годится: он отдаёт тело целиком, и ответ,
который не кончается, не вернётся никогда. Что у потока то же, что
у запроса, — и собирается тем же кодом: адрес с параметрами, заголовки
клиента и запроса, тело (`json`, `form`, `body`), проверка сертификата,
клиентский сертификат, сокет, срок открытия (`connect_timeout + timeout`).

| Вызов | Что делает |
|---|---|
| `client:stream({ max_body, max_piece, duplex, … })` | `max_body` — сколько байт поток отдаст за жизнь, `0` — без предела, по умолчанию предел клиента; `max_piece` — сколько байт в одном куске, `0` (умолчание) — без предела; `duplex` — держать отправку открытой |
| `stream:read(what, timeout)` | `what` — число байт или разделитель, по умолчанию строка `'\n'`; `timeout` — по умолчанию срок ответа |
| `stream:write(data, timeout)` | дописывает тело; только у потока с `duplex = true` |
| `stream:close()` | закрывает; повторно — безопасно |
| `stream.status`, `stream.headers` | код — когда поток кончился; заголовки — у методов без тела |

Исходы чтения: кусок — непустая строка; `nil` без отказа — поток
кончился удачно; `nil` с отказом `idle` — за срок куска не набралось,
но поток открыт, и следующее чтение продолжит с того же места; любой
другой отказ поток закрыл. Читать после конца можно: вернётся то же,
чем поток кончился. Это касается и закрытия из другого файбера посреди
чтения или записи: ждавший получит итог закрытия (`invalid`, «поток
закрыт»), а не обрыв, которым libcurl на закрытие ответил, — так
остановку можно отличить от сети.

У потока пределов два, и оба — счёт отданного: `max_body` — сумма
за всю жизнь потока, `max_piece` — длина одного куска. Бесконечному
потоку сумму ставят нулём, и длину строки держит тогда предел куска;
без обоих длина куска не ограничена ничем. Кусок, переваливший предел,
не отдаётся, и поток закрывается отказом `refused`: «поток больше предела
в N байт» за сумму, «кусок больше предела в N байт» за кусок. Кусок при
чтении до разделителя — строка вместе с разделителем. Чтению байтами
предел куска ставит само число: просить байт больше `max_piece` — отказ
`invalid` до чтения, и поток остаётся открытым.

Тело потока шлётся только у POST, PUT и PATCH (прочим `http.client` его
не отправляет, и тело у них — отказ `invalid` до открытия), и после тела
отправка закрывается: сервер, дочитывающий тело запроса, иначе ждал бы
продолжения. Держать отправку открытой — `duplex = true`: так подписка
наблюдения etcd дописывается в уже открытый поток. Пустая запись у
`http.client` закрывает отправку совсем, поэтому `write` берёт только
непустую строку.

Чего у потока нет, и это решение:

- **повторов** — прочитанное уже отдано, повтор с начала отдал бы его
  второй раз; переподключается тот, кто знает, с какого места продолжать;
- **переходов** — код приходит в конце, узнать о переходе раньше нечем;
- **слоёв** — слой получает и возвращает ответ, а поток ответом
  не является;
- **записей в журнал** — отказ уходит парой, а поток, переподключаемый
  раз в секунду, залил бы журнал.

Чем заплачено за `http.client` (всё проверено запуском на 3.8):

- **код ответа известен только в конце**: поток, на который сервер
  ответил 404, отдаёт страницу ошибки кусками, и лишь последнее чтение
  говорит отказом `status`; кому нельзя принять страницу ошибки
  за данные, тот проверяет разбор каждого куска;
- **открытие ждёт первого куска тела**, а не заголовков: сервер,
  приславший заголовки и замолчавший, даёт отказ по сроку открытия;
  у POST, PUT и PATCH открытие возвращается, как только libcurl готов
  слать;
- **заголовки видны только у методов без тела**;
- **обрыв посреди тела выглядит концом**, и отличает его только код после
  `finish` — 0 вместо кода сервера; клиент это различает и отдаёт
  `unreachable`;
- **чтение с нулевым сроком отдаёт пустую строку**, ту же, что настоящий
  конец, — поэтому срок короче миллисекунды поток отвергает;
- **срок чтения выходит двумя путями**: на молчании `http.client` бросает
  исключение, а на потоке, шлющем байты без разделителя, возвращает `nil`,
  когда срок истёк посреди куска; оба пути поток отдаёт одним отказом
  `idle`;
- **обратного давления нет** (см. «Пределы»): тело копится у
  `http.client`, пока поток открыт, и память ограничена только скоростью
  чтения.

Закрывать поток обязательно. Файберов он не заводит; соединение держит
libcurl и отпускает его только закрытие — брошенный без `close` поток
сервер продолжает кормить (на опыте сервер не заметил обрыва и через
секунду после сборки мусора). На отказе поток закрывается сам.

### Слои

Клиент принимает слои — функции вида `function(request, nxt)`, обёрнутые
вокруг отправки: подпись запроса, журнал, кэш. Договор слоя тот же, что
у [`tnt-middleware`](https://github.com/tnt-skein/tnt-middleware).

```lua
local function signing(request, nxt)
    request.headers['x-signature'] = sign(request.method, request.path, request.body)

    return nxt(request)
end

local api = assert(http.new({ base_url = 'https://api.example.org/v1', layers = { signing } }))
```

Слой видит запрос в общем виде перед отправкой — `method` заглавными,
`url` вместе с параметрами, `path` без них, `query`, `headers` с именами
в нижнем регистре, `body` уже строкой — и ответ после. Слои идут снаружи
внутрь в порядке перечисления: первый видит запрос первым и ответ
последним. Слой вправе не пустить запрос дальше вовсе: его отказ —
строка или таблица `{ message, retriable }` — доходит вызывающему
отказом рода `refused` и пишется в журнал. Слои оборачивают каждую
попытку, а не вызов: повтор проходит их заново. У потока слоёв нет.
Трассу слоем не ставят: она едет сама, см. ниже.

### Опознаватель запроса и трасса

Записи одного запроса на двух узлах связывает опознаватель, который
обязан доехать до чужой службы. Клиент довозит его сам, и прикладной код
для этого не пишет ни строки:

```lua
local context = require('tnt.context')

context.run({ request_id = 'r-7' }, function()
    api:get('/customers/7')                        -- x-request-id: r-7
    local events = api:stream({ url = '/events' }) -- и у потока тот же заголовок
    events:close()
end)
```

**Заголовки — из контекста файбера, без всякой установки.** В каждую
попытку запроса и в открытие потока клиент кладёт `context.export()`
из `tnt-context`: ключи контекста, у которых объявлен заголовок. Это
`x-request-id`, а внутри трассы — `traceparent` и `tracestate`, которые
кладёт в контекст тот, кто ведёт трассу. От трассировки клиент
**не зависит** и правил W3C не знает: он отдаёт наружу то, что контекст
назвал заголовком. Поэтому забытая установка трассировки заголовков
не рвёт — теряются только клиентские отрезки.

Правила, и каждое проверено:

- заголовок, заданный вызывающим — настройкой клиента, обращения, слоем
  или крюком, — главнее контекста и не перезаписывается;
- вне всякой области контекста заголовков нет; в области без трассы
  уходит только `x-request-id`;
- заголовки едут через переходы по `Location`, в том числе на чужой
  узел: W3C рассчитывает на пересылку, а `x-request-id` — опознаватель,
  не тайна (тайна входа, `Authorization`, на чужой узел не едет);
- каждая попытка идёт по своей копии запроса: то, что крюк, слой или
  контекст дописали в заголовки одной попытки, до следующей
  не доезжает — иначе заголовок трассы второй попытки нёс бы отрезок
  первой, лёжа в заголовках как «заданный вызывающим».

**Крюки — именованный список модуля.** Клиентский отрезок трассы
на попытку — её длительность, исход, повтор отдельной операцией — это
знание трассировки, а не клиента, и приходит оно крюком:

```lua
local clock = require('clock')
local log = require('tnt.log').new('app.http')

http.hook('timing', function(call, proceed)
    -- call.kind: 'request' — попытка запроса с её переходами, 'stream' — открытие потока
    -- call.attempt: номер попытки с единицы; у потока nil
    -- call.request: запрос в общем виде; заголовки можно дописать до proceed
    local started = clock.monotonic()
    local answer, err = proceed()

    log.info('исходящее обращение', {
        kind = call.kind,
        attempt = call.attempt,
        method = call.request.method,
        elapsed = clock.monotonic() - started,
    })

    return answer, err
end)

http.hooks()               --> { 'timing' }; то же в client:status().hooks
http.hook('timing', nil)   -- снять
```

Крюк трассировки устроен так же: у попытки запроса он исполняет
`proceed` внутри клиентского отрезка `HTTP <метод>`, закрывая отрезок
по исходу, а вне трассы — просто зовёт `proceed`.

- Крюки идут **снаружи внутрь в порядке постановки**; слои клиента —
  внутри крюков; заголовки контекста собираются внутри `proceed`, после
  всех, — так заголовок трассы несёт отрезок, который завёл крюк, а не
  отрезок вызывающего. Крюк вправе исполнить `proceed` в своей области
  контекста.
- `proceed` отправляет **один раз**, и его итог — итог попытки: что
  вернул крюк, позвавший `proceed`, не читается. Повторный вызов
  `proceed` отдаёт прежний итог, а не шлёт запрос второй раз.
- Крюк зовётся под `pcall`. Бросивший **до** `proceed` — клиент
  отправляет сам; бросивший **после** — итог отправки не теряется.
  О сорвавшемся пишется `warn` с его именем (`hook`), родом (`kind`)
  и методом, с подавлением повторов подряд: сломанная телеметрия
  не стоит запроса, но и молчать о ней нельзя.
- Крюк, вернувшийся без `proceed`, отменил отправку — как слой: ответ,
  который он вернул, — ответ; `nil, причина` — отказ рода `refused`;
  пустота — отказ `refused` с именем крюка («крюк «имя» не отправил
  обращение и не назвал причины»).
- Замена под тем же именем оставляет крюк на прежнем месте в порядке
  и безвредна: установку трассировки зовут и при старте, и при
  перечитывании настроек. Снятый и поставленный снова встаёт последним.
- Имя — непустая строка, крюк — функция или `nil`; иное — исключение
  на строке вызывающего.

**Список крюков — общий на процесс, и это нарочно.** Клиенты собираются
и внутри других пакетов — клиент хранилища конфигурации, приёмник
уведомлений, транспорт отчётов об ошибках, — и до их настроек приложение
не дотягивается; крюк, поставленный настройкой одного клиента, терялся бы
ровно там, где клиент собран не приложением. Одна внешняя зависимость
через `tnt-external` не годится тоже: слот у неё один, а крюков бывает
два — трасса и крошки отчёта об ошибках. Проверки снимают свои крюки
`http.hook(name, nil)`.

**`propagate = false` снимает и заголовки, и крюки** — настройкой
клиента, не обращения:

```lua
local exporter = assert(http.new({ base_url = 'http://otel-collector:4318', propagate = false }))
```

Она обязательна клиентам, которые шлют саму телеметрию — выгрузчику
трасс, транспорту отчётов об ошибках: иначе выгрузка отрезка рождала бы
отрезок о самой себе. Её же ставят клиенту к недоверенной службе,
которой опознаватели знать незачем. Решение о том, кому доверять,
принимают при сборке клиента, а не на каждом вызове. В `status()` видны
`propagate` и `hooks`.

### Что можно подставить вместо клиента

`tnt.http.transport` объявляет libcurl внешней зависимостью через
`tnt-external`: её подменяют проверки самого пакета, и подмена глобальна.
Прикладной код подменяет не её, а экземпляр клиента: достаточно таблицы
с `request(opts)`, `stream(opts)` и `status()`. Поле `handle` в этот
договор не входит — это обработчик libcurl самого клиента, и мимо фасада
через него не ходят. Двойник вправе отказывать и строкой: вызывающий
читает отказ через `tostring`.

```lua
local double = {
    request = function(_, opts)
        return { status = 200, headers = {}, body = '{"id":7}', json = function() return { id = 7 } end }
    end,
    stream = function()
        return nil, 'поток не нужен'
    end,
    status = function()
        return {}
    end,
}
```

### Что не попадает в журнал

Клиент пишет в журнал `tnt-log` под именем `tnt.http` две вещи:
неудавшийся запрос (`warn` «запрос не удался») и сорвавшийся крюк.
Метод, узел и путь — попадают. **Строка запроса — нет**: в параметрах
ездят ключи доступа, а журнал читают все; причина пишется без адреса
(`reason`). Ответ с любым кодом — не отказ, и в журнал не пишется.
`status()` показывает имена заголовков без значений по той же причине,
а ключ сертификата — только признаком. Поток в журнал не пишет ничего,
кроме записи о сорвавшемся крюке при открытии.

### Что настроено: `status`

```lua
api:status()
--> {
-->     base_url = 'https://api.example.org/v1', timeout = 3, connect_timeout = 3,
-->     max_redirects = 3, max_body = 1048576, max_connections = 8, verify = true,
-->     ssl_key = false, user_agent = 'tnt-http', headers = { 'authorization' },
-->     layers = 0, propagate = true, hooks = {}, retry = { attempts = 3, … },
--> }
```

Значения заголовков не показываются никогда: в `authorization` лежит
пароль, а состояние читают и журнал, и панель, и человек через плечо.

## Чем пришлось поступиться

**libcurl, а не свой сокет.** Под клиентом — `http.client`: TLS
с проверкой сертификата и цепочки, HTTP/2, `chunked`, сжатие,
повторное использование соединений, прокси, IPv6 уже написаны,
проверены миллионом узлов и не стоят ни строки. Свой клиент поверх
сокета пришлось бы начать с разбора заголовков и `Transfer-Encoding`,
а кончить своим кэшем соединений; ошибка в любом из этих мест выглядит
как «иногда теряется ответ» и ищется неделями. Цена — всё, что libcurl
не даёт: предел размера только счётом отданного, общий срок вместо
раздельных, поток без обратного давления (см. «Пределы» и «Сроки»).

**Пула соединений сверху нет.** Кэш соединений живёт внутри libcurl
и настраивается `max_connections`. Второй пул поверх него стерёг бы
не соединения, а обработчики libcurl, а закрыть обработчик в Tarantool
нечем — пул, выбрасывающий простаивающие, тёк бы ими. По той же причине
у клиента нет «закрыть»: `configure` забывает прежний общий клиент,
а не закрывает его.

**Крюки — состояние, общее на процесс.** Клиент, собранный внутри
другого пакета, иначе остался бы без трассы (см. «Опознаватель запроса
и трасса»). Цена — проверки обязаны снимать свои крюки сами.

**Заголовки контекста уходят во всякую службу.** `x-request-id`
и заголовки трассы едут и в чужую службу тоже. Для опознавателей это
безвредно: W3C рассчитывает именно на пересылку, а значение
`x-request-id` ограничено объявлением ключа — длина, отсутствие
управляющих знаков, UTF-8. Тайнам в контексте не место, и это правило
`tnt-context`, а не клиента; кому не нужно и это, ставит
`propagate = false`.

**`Retry-After` — только числом секунд.** Дату клиент не разбирает:
она меряется часами сервера. Сервер, назвавший дату, получит обычную
паузу по отступу.

**Белый список настроек.** Незнакомое имя — отказ, но и всё, чего
в списке нет, до libcurl не доходит. Однажды это уже отрезало нужное —
клиентские сертификаты, — и это полгода читалось как «Tarantool
не умеет». Поэтому список опций ядра перечислен здесь целиком (сверено
с исходником и строками бинарника 3.8):

| Опция `http.client` | У клиента | Почему |
|---|---|---|
| `timeout` | `timeout` + `connect_timeout` | см. «Сроки» |
| `headers`, `params` | `headers`, `query` | параметры кодирует свой кодировщик, один с телом формы |
| `ca_file`, `ca_path` | так же | |
| `verify_peer`, `verify_host` | одна `verify` | сертификат, выданный на чужое имя, не защищает ни от чего: выключить одну проверку без другой — ошибка, а не настройка |
| `ssl_cert`, `ssl_key`, `unix_socket` | так же | см. «Клиентский сертификат и сокет» |
| `accept_encoding` | так же | выключить сжатие им нельзя: пустая строка у libcurl просит все сжатия, какие он умеет, а `identity` лишь просит — сжатое вопреки просьбе тело libcurl всё равно разожмёт (проверено). Не разжимает он только без опции вовсе, а клиент ставит умолчание. У потока умолчание то же, что у запроса, нарочно: сжатие лишь ускоряет набивку памяти, а без обратного давления её набивает и несжатый поток |
| `follow_location` | всегда `false` | переходы проходит клиент: иначе их не сосчитать и не снять `Authorization` |
| `chunked` | `client:stream` | |
| `max_connections` (у `new`) | так же | |
| `max_total_connections` (у `new`) | нет | не было нужды; кэш соединений держит `max_connections` |
| `proxy`, `proxy_port`, `no_proxy` | нет | не было нужды; libcurl читает `http_proxy` и `no_proxy` из окружения сам. Если понадобится — брать все три вместе |
| `proxy_user_pwd` | нет | тайна: если появится, в `status()` и в журнал не попадает, как пароль |
| `interface` | нет | выбирать исходящий интерфейс узла — дело сети, а не приложения |
| `http_version` | нет | libcurl договаривается о версии сам; принудительная версия нужна для отладки, а не в бою |
| `keepalive_idle`, `keepalive_interval` | нет | не было нужды; ручки не везде работают («non-universal» в самом ядре) |
| `low_speed_time`, `low_speed_limit` | нет | это срок тишины, а не срок соединения: при `timeout = 3` и `low_speed_time = 1` за секунду оборвались и недоступный адрес, и принявший соединение сервер, который думает (проверено). Отдельного срока соединения из них не собрать, а поток, молчащий между событиями, они бы рвали |
| `max_header_name_length` | нет | умолчания ядра (32) достаточно |
| `verbose` | нет | пишет заголовки запроса в журнал Tarantool, вместе с `Authorization` |

## Проверки

Проверки лежат в `test/` и идут на luatest: `.rocks/bin/luatest test/`.
Модули пакета берутся из исходников, зависимости — установленными.

libcurl подменён двойником через внешнюю зависимость
`tnt.http.transport`: двойник помнит, о чём его просили, и отдаёт
заранее написанные ответы по порядку — переходы и повторы видны только
по порядку обращений. Двойник потока пересказывает то, что
`http.client` отдавал на опытах: код только после `finish`, срок чтения
исключением и пустым возвратом, обрыв пустой строкой. Часы цикла
повторов подменены: пауза двигает их сама, и три попытки с отступом
стоят миллисекунды. Контекст — настоящий: заголовки берутся из хранилища
файбера тем же путём, что и в бою. Журнал ловится ловушкой: что
строка запроса в запись не попала, видно только по записи.

Пересказ двойника сверяют пять живых проверок против настоящего
libcurl:

- `socket_live_test` и `hostile_live_test` поднимают свои серверы сами —
  на сокете во временном каталоге и на свободном порту — и докера
  не требуют; первой нужен рок `http`. Враждебный сервер льёт тело без
  пауз и без разделителя, молчит после первой строки до закрытия
  и отвечает переходом на `file://`;
- `http_live_test` и `stream_live_test` идут против httpbin на
  `127.0.0.1:18080`, `tls_live_test` — против etcd с `--client-cert-auth`
  на `127.0.0.1:12391`, с корнем и сертификатами в `ETCD_MTLS_DIR`
  (по умолчанию `test/stand/run/etcd-mtls`).

```sh
test/stand/httpbin.sh            # httpbin в докере: запросы и поток
test/stand/etcd_mtls.sh          # выпускает сертификаты на сутки и поднимает etcd
test/stand/httpbin.sh stop
test/stand/etcd_mtls.sh stop
```

Без стенда три последние проверки пропускаются: гейты не должны зависеть
от докера.
